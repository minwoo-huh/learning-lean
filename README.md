## 3. 계산 결과와 증명은 어떻게 다른가?

다음을 한 줄씩 입력하고, 각 줄에 커서를 놓아 메시지를 확인합니다.

```lean
#eval 2 + 3
#check (2 + 3 : Nat)
#check (2 + 3 = 5)
```

첫 줄은 계산해서 `5`를 보여줍니다. 둘째 줄은 수식의 타입이 `Nat`, 즉 자연수임을 보여줍니다. 셋째 줄은 “2 + 3 = 5”가 `Prop`, 즉 명제임을 보여줍니다.

**명제를 적는 것과 그 명제를 증명하는 것은 별개의 일입니다.** 다음 줄도 명제로서 올바른 형태입니다.

```lean
#check (2 + 3 = 6)
```

이 명제가 `Prop`이라는 사실은 참이라는 뜻이 아닙니다. Python에서 어떤 식의 타입이 `bool`이라고 해서 그 값이 반드시 `True`인 것은 아닌 것과 비슷하게 생각할 수 있습니다. 다만 Lean의 `Prop`과 계산용 `Bool`은 서로 다른 개념입니다.

실제 증명은 다음처럼 씁니다.

```lean
example : 2 + 3 = 5 := by
  rfl
```

* `example`: 이름을 붙이지 않는 예제 정리를 선언합니다.
* `:` 뒤: 증명할 명제입니다.
* `:= by` 뒤: 전술을 사용해 증명을 작성합니다.
* `rfl`: 양쪽이 정의에 따른 계산으로 같아지는 등식을 증명합니다.

여기서는 `2 + 3`이 `5`로 계산됩니다. `rfl`은 모든 참인 등식을 자동으로 푸는 명령이 아닙니다.

**확인 질문:** `#check (2 + 3 = 6)`에 오류가 없는데도 그 명제가 증명된 것은 아닌 이유를 말해보세요.

## 4. 명제와 그 증거: `P : Prop`, `hP : P`

선형대수학에서 “벡터 x가 공간 V에 속한다”는 표현에 익숙할 것입니다. Lean에서 `x : Nat`은 “x의 타입이 자연수”라는 뜻입니다.

증명에서도 콜론을 사용합니다.

```lean
example (P : Prop) (hP : P) : P := by
  exact hP
```

* `P : Prop`: P는 명제입니다.
* `hP : P`: hP는 P의 증거입니다. 이 예제에서는 가정으로 받습니다.
* 마지막 `: P`: 지금 증명해야 할 결론도 P입니다.
* `exact hP`: 필요한 결론 P의 증거로 hP를 제출합니다.

이 예제는 임의의 P가 저절로 참이라고 말하지 않습니다. **P의 증거가 주어지면 P를 증명할 수 있다**는 조건부 주장입니다.

`hP`라는 이름에는 특별한 기능이 없습니다. `evidence`로 바꾸어도 되며, 그때 마지막 줄도 `exact evidence`로 바꾸면 됩니다.

### Infoview 읽기

증명 시작 부분에 커서를 놓으면 대략 다음과 같은 상태를 볼 수 있습니다.

```
P : Prop
hP : P
⊢ P
```

가로선 대신 `⊢`를 경계로 생각하세요.

* 위쪽: 사용할 수 있는 대상과 가정.
* `⊢` 오른쪽: 지금 만들어야 할 증거의 타입, 즉 증명 목표.

`exact hP`를 처리한 뒤 남은 목표가 없으면 이 예제의 증명이 끝납니다. 커서 위치에 따라 명령 전후의 상태가 보일 수 있으니 줄 끝이나 다음 줄로 이동해보세요.

## 5. 함수 호출로 이해하는 `exact`

이제 P이면 Q이고, P가 참이라는 가정에서 Q를 증명합니다.

종이 증명은 한 문장입니다. “P가 성립하고 P이면 Q이므로 Q가 성립한다.”

```lean
example (P Q : Prop) (hP : P) (hPQ : P → Q) : Q := by
  exact hPQ hP
```

`hPQ : P → Q`는 P의 증거를 받아 Q의 증거를 돌려주는 함수처럼 사용할 수 있습니다. Lean의 함수 적용은 `hPQ(hP)` 대신 보통 `hPQ hP`처럼 씁니다.

| 표현       | 타입      | 읽는 방법                 |
| -------- | ------- | --------------------- |
| `hP`     | `P`     | P의 증거                 |
| `hPQ`    | `P → Q` | P의 증거에서 Q의 증거를 만드는 함수 |
| `hPQ hP` | `Q`     | hPQ에 hP를 넣어 얻은 Q의 증거  |

여기서 “명제는 타입처럼, 증명은 그 타입의 값처럼 다룬다”는 연결을 처음 만납니다. 의존 타입 이론 전체를 지금 공부할 필요는 없습니다. 오늘은 이 짧은 함수 적용이 납득되면 충분합니다.

### 작은 실험

마지막 줄을 잠시 `exact hP`로 바꿔보세요.

왜 실패할까요? 필요한 것은 Q의 증거인데 제출한 hP의 타입은 P이기 때문입니다. 오류 문구를 전부 외우기보다 **제출한 타입과 기대한 타입**을 비교하세요. 확인한 다음 원래 코드로 되돌립니다.

## 6. 목표에서 거꾸로 생각하는 `apply`

같은 문제를 다음처럼 풀 수 있습니다.

```lean
example (P Q : Prop) (hP : P) (hPQ : P → Q) : Q := by
  apply hPQ
  exact hP
```

처음 목표는 Q입니다. `apply hPQ`는 “hPQ를 사용해 Q를 만들려면 무엇이 필요한가?”를 묻습니다. hPQ가 P를 입력으로 요구하므로 목표가 P로 바뀝니다.

```
처음:        ⊢ Q
apply hPQ:   ⊢ P
exact hP:    남은 목표 없음
```

`apply`는 P를 참이라고 가정해버리는 명령이 아닙니다. **P를 증명해야 할 새 의무로 남깁니다.**

* `exact hPQ hP`: 완성된 Q의 증거를 한 번에 제출.
* `apply hPQ`: Q를 만드는 방법을 선택하고, 필요한 P의 증거는 다음 단계에서 제출.

둘은 같은 수학적 추론을 서로 다른 방향으로 작성한 것입니다.

**잠깐 멈추기:** `apply hPQ` 직후 왜 목표가 Q가 아니라 P인지 자기 말로 설명해보세요.

## 7. 함의를 증명할 때는 `intro`

이번에는 P의 증거를 처음부터 가정으로 받지 않습니다. 목표 자체가 “P이면 P”입니다.

```lean
example (P : Prop) : P → P := by
  intro hP
  exact hP
```

종이 증명에서는 “P라고 가정하자. 그러면 P이다”라고 씁니다.

`intro hP`는 함의의 앞부분 P를 새 가정 hP로 받아들이고, 결론 P를 목표로 남깁니다.

```
처음:
P : Prop
⊢ P → P

intro hP 이후:
P : Prop
hP : P
⊢ P
```

프로그래밍 관점에서는 입력을 받은 뒤 그 입력을 그대로 반환하는 항등함수와 연결됩니다. 다음은 같은 명제의 다른 증명입니다.

```lean
example (P : Prop) : P → P :=
  fun hP => hP
```

오늘은 `by`를 사용하는 첫 번째 형태에 익숙해지세요.

## 8. 직접 풀어보기

다음 네 예제를 실습 파일 아래에 붙여 넣으세요. **`sorry`를 지우고 증명으로 교체**합니다. 완성 코드를 복사하기 전에 각 문제에 최소 3분은 직접 시도하세요.

### 문제 1 — 맞는 증거 고르기

```lean
example (P Q : Prop) (hP : P) (hQ : Q) : Q := by
  sorry
```

목표와 같은 타입의 가정은 무엇인가요?

### 문제 2 — 두 번 연결하기

```lean
example (P Q R : Prop)
    (hP : P) (hPQ : P → Q) (hQR : Q → R) : R := by
  sorry
```

먼저 `apply`와 `exact`로 풀고, 가능하면 `exact` 한 줄로도 풀어보세요.

### 문제 3 — 입력을 받고 연결하기

```lean
example (P Q R : Prop)
    (hPQ : P → Q) (hQR : Q → R) : P → R := by
  sorry
```

문제 2와 비교하면 어떤 가정이 사라졌고, 대신 목표가 어떻게 바뀌었나요?

### 문제 4 — 함수 계산과 등식

```lean
def shiftByThree (n : Nat) : Nat := n + 3

example : shiftByThree 4 = 7 := by
  sorry
```

`shiftByThree`의 정의를 따라 계산하면 양쪽은 무엇이 되나요?

막히면 [1강 힌트와 해설](lecture-01-solutions.md)을 여세요. 먼저 힌트까지만 읽고 돌아와서 다시 시도하는 것을 권합니다.

## 9. `sorry`와 “검증됐다”의 의미

`sorry`는 “여기는 나중에 증명하겠다”는 자리표시자입니다. 남은 목표가 사라져 보이더라도 그 부분의 논리적 근거를 제공한 것은 아닙니다.

다음 예제는 **미완성 코드의 예시**이므로 완성된 풀이에 포함하지 마세요.

```lean
example : 2 + 3 = 6 := by
  sorry
```

학습 중에는 틀을 만들기 위해 쓸 수 있지만, 완료 표시를 하기 전에는 지워야 합니다.

연구 수준의 “Lean 검증”을 이해할 때도 두 질문을 구분합니다.

1. 적어 놓은 형식 명제에 대해, 어떤 가정과 공리로 증명을 구성했는가?
2. 그 형식 명제가 우리가 의도한 수학적 주장과 정확히 같은가?

오늘은 P와 Q의 짧은 예제로 이 차이를 익힙니다. 나중에는 같은 관점으로 해석학 정리의 가정과 결론을 읽게 됩니다. 더 자세한 기준은 [Lean 커뮤니티의 검증 안내](https://leanprover-community.github.io/did_you_prove_it.html)를 참고하세요.

## 10. 자주 막히는 지점

| 증상                    | 먼저 확인할 것                                |
| --------------------- | --------------------------------------- |
| `exact hP`가 실패함       | hP의 타입과 현재 목표가 같은가?                     |
| `apply hPQ` 뒤에 오류가 남음 | 새로 생긴 P라는 목표를 아직 증명하지 않았는가?             |
| `unknown identifier`  | 이름을 잘못 썼거나, 해당 가정이 없는 다른 예제에 있는가?       |
| 들여쓰기 관련 오류            | `by` 아래의 증명 줄을 같은 깊이로 들여썼는가?            |
| Infoview가 비어 있음       | `.lean` 파일과 프로젝트를 열었고, 증명 내부에 커서를 놓았는가? |
| 코드가 통과한 것 같은데 경고가 있음  | `sorry`가 남아 있는가?                        |

다음 예제로 이동하면 이전 예제의 hP 같은 가정은 자동으로 따라오지 않습니다. 각 `example`의 괄호 안에서 어떤 대상을 받았는지 다시 확인하세요.
